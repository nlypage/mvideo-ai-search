### 2. Починить пустую строку над статусом ИИ

**Проблема.** В `B2EConsole.send()` сразу пушится `{ role: "assistant", text: "" }`. Пустой бабл рендерится с padding/border, появляется «лишняя строка» над `AgentStreamStatus`.

**Решение.** Сделать как в `SearchResults.tsx`:

- НЕ добавлять пустое assistant-сообщение заранее. Хранить `currentStreamingId` отдельным state (или вычислять `assistantId` лениво при первом дельта-чанке).
- В `onDelta`:
  1. Если ещё нет сообщения с этим id - вставить его в `messages`.
  2. Иначе - дописать чанк.
- В `onEvent`/`finally` ничего пушить, если ассистент так и не выдал текст (например, ошибка) - в этом случае вставить сообщение об ошибке.
- В рендере: пустые assistant сообщения (`text === ""` и нет `products`) НЕ рендерить.
- `AgentStreamStatus` показывать только пока `loading && (нет последнего assistant с текстом)`.

Acceptance: при отправке запроса визуально появляется только индикатор статуса, без серого пустого пузыря.

### 3. Частичное одобрение позиций из плана

**Проблема.** Сейчас в плане допродажи две кнопки «Клиент одобрил» / «Отказался» на весь набор. Реально клиент может взять 1 из 3.

**Решение.**

- Расширить state `plan`:
  ```ts
  type PlanItemStatus = "pending" | "approved" | "declined";
  type Plan = {
    status: "open" | "closed";
    items: { product: Product; status: PlanItemStatus }[];
  };
  ```
- Каждая позиция в списке плана получает 3-состояния:
  - чекбокс/чип «Взял» (зелёный),
  - кнопка «Отказался» (серая),
  - дефолт - «pending» (нейтральная).
  - Клик по «Взял» переключает в approved; клик по «Отказался» - в declined; повторный клик - сбрасывает в pending.
- Внизу карточки плана:
  - Сводка: «Взято: X · Отказ: Y · Ожидает: Z».
  - Считать «фактический средний доп. процент» только по `approved` позициям.
  - Кнопка «Закрыть консультацию» переводит `status: "closed"` и блокирует переключатели; после этого показывается итог.
- Когда план открыт, новый ответ ассистента с другими товарами не должен затирать уже размеченный план без подтверждения. Варианты (выбери первый):
  1. Если есть pending позиции - спросить (toast/inline-кнопка «Заменить план»).
  2. Если все позиции уже approved/declined - автоматически закрыть текущий план в «историю смены» и открыть новый.
- Добавить простую «историю смены» в нижней части сайдбара (см. блок 5).

Acceptance: можно отметить 1 товар как «взят», 2 как «отказ», увидеть корректный средний %, закрыть план.

### 4. Навигация / вкладки: убрать вводящее в заблуждение «Каталог»

**Проблема.** В сайдбаре активна вкладка «Каталог», хотя пользователь работает в ИИ-помощнике. «Склад» и «Профиль» задизейблены и непонятны.

**Решение.**

- Переименовать и переставить вкладки на актуальные роли консультанта:
  1. **Ассистент** (иконка `Sparkles`) - активна по умолчанию, это текущий экран.
  2. **План дня** (иконка `Target`/`TrendingUp`) - демо-экран со скрипт-карточками: текущий KPI (62%), список последних обслуженных клиентов из «истории смены» (см. блок 3), кнопка «Открыть смену/Закрыть смену». Можно реализовать как простую панель без реальной логики.
  3. **Каталог** (`LayoutGrid`) - быстрый ручной поиск по каталогу M.Видео (переиспользует `searchCatalogProducts` из `mv-llm.ts`), без ИИ. На странице - поисковая строка + grid `ProductCard` (компактный, с Stock и Margin). Полезно показать «я могу быстро глянуть остатки и без чата».
  4. **Профиль** - оставить, но сделать минимально живым: показывать имя, магазин, ставку, накопленный бонус смены (сумма margin по approved позициям всех закрытых планов в сессии).
- Активную вкладку подсвечивать корректно (сейчас «Каталог» подсвечен даже когда мы на ассистенте - убрать).
- Заглушку «Скоро будет доступен» удалить - все четыре вкладки должны быть кликабельны.
- Состояние вкладки - в `useState<ConsoleTab>("assistant")`. Контент рендерить через `switch (active)`.
- Mobile-версия (`grid-cols-3`) - переделать на 4 колонки или горизонтальный скролл.

Acceptance: открывая страницу B2E, видишь активную вкладку «Ассистент»; переключение по всем 4 вкладкам работает и показывает разный контент.

## Жёсткие правила для исполнителя

- НЕ трогать клиент M.Видео API (`backend/internal/clients/mvideo/*`) кроме случая, если нужно вынести `enrichB2EProducts` (но логичнее держать обогащение в слое agent, не в клиенте - данные «демо», не должны протекать в B2C).
- НЕ ломать B2C поток - все изменения общих компонентов (`ProductCard`, `AgentStreamStatus`, `mv-llm.ts`) должны быть обратно совместимы.
- НЕ использовать длинное тире/эм-дэш в русских текстах UI - только обычный дефис `-`.
- НЕ городить sanitizer-хаки над промптом - править сам промпт.
- Тон ассистента в B2E - «коллега», не «модель». Не писать «Готовлю ответ модели…», писать «формулирую подсказку».
- Все новые тексты UI - на русском, коротко и по-человечески.
- Перед сдачей: убедиться, что `npm run build` и `go test ./...` зелёные.
